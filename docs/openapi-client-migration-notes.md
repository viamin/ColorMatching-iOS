# OpenAPI Client Migration — Research Notes (issue #5)

Working notes for replacing the hand-written `ColorMatchingLPSAppCore/APIClient.swift`
layer with a client generated by `swift-openapi-generator`. This run only adds
tests (`iOS/Tests/ColorMatchingLPSAppTests/OpenAPIContractGapTests.swift`,
`OpenAPISpecVendoringTests.swift`) and these notes; the generator wiring,
vendored spec, and generated types are implementation work for a follow-up run.

## Dependency status (viamin/color_matching#110)

Checked 2026-11-01 via the public GitHub pages (no API access to that repo from
this environment — the GitHub proxy available here is scoped to this repo only):

- Issue #110 is **closed** ("completed"), closed by **PR #113**, merged
  2026-10-30 into `main`.
- The PR adds `OpenApiSpex` schema/operation annotations across
  `lib/color_matching_web/controllers/*` and `lib/color_matching_web/api_schemas.ex`.
- **The spec is generated at runtime and served at `GET /api/v1/openapi.json`.**
  It is not a static file committed to the `color_matching` repo, so there is
  nothing to vendor directly from source control.

### Blocker: no live server to fetch the spec from

This environment has no network path to a running `color_matching` instance
(no database/services per this repo's environment constraints), so the actual
`GET /api/v1/openapi.json` response could not be fetched or vendored in this
run. The implementation run needs one of:

- Network access to a deployed/staging `color_matching` instance, to
  `curl $BASE_URL/api/v1/openapi.json -o iOS/Sources/ColorMatchingLPSAppCore/openapi.json`, or
- Running the Phoenix app locally (`mix phx.server`) and fetching from
  `localhost`, or
- The `color_matching` maintainers publishing a static spec artifact (e.g. as
  a release asset or committed file) that doesn't require a live server.

`OpenAPISpecVendoringTests.testOpenAPIDocumentIsVendoredForGeneration` fails
until one of the files above exists at
`iOS/Sources/ColorMatchingLPSAppCore/openapi.json` (or `.yaml`) — the
conventional location `swift-openapi-generator`'s config and generator plugin
expect, next to the target that will consume the generated types
(`ColorMatchingLPSAppCore`).

## Preliminary contract deltas (unverified — re-check against the real spec)

These were inferred by reading `color_matching`'s source
(`lib/color_matching_web/api_schemas.ex`, `capture_controller.ex` on `main`)
through GitHub's web UI, **not** the actual generated OpenAPI document — the
source can diverge from what `OpenApiSpex` emits, and the summarization tool
used to read it truncates long quotes. Treat every item below as a lead to
confirm directly against `GET /api/v1/openapi.json` before changing any
generated type mapping, not as settled fact.

1. **`linear_rgb_median` / `normalized_linear_rgb_median` are polymorphic
   (`RgbPayload`)**: object `{r,g,b}`, a flat 3-number array, or a
   JSON-encoded string — not just the object form the hand-written `RGB`
   `Codable` struct supports today. Covered by
   `OpenAPIContractGapTests` (red until the generated/replacement client
   handles all three forms).
2. **`MeasurementUploadRequest` has no top-level `scoring_algorithm_version`**
   in the real schema — only `measurements` and an *optional* `pair_scores`
   array. The prose contract (`docs/color-matching-api-contract.md`) and the
   current `APIClient.uploadMeasurements` both send a top-level
   `scoring_algorithm_version` field that the real schema doesn't document.
   Per-score `algorithm_version` (on `PairScoreRequest`, required) already
   matches what `PairScore` sends.
3. **`PrinterProfile.id` is an integer** in the real schema; the prose
   contract's manifest example shows a string-like id
   (`"printer_profile_1"`). The hand-written `SheetManifest` doesn't decode
   `printer_profile` at all today, so this hasn't surfaced as a runtime bug —
   confirm the generated type before wiring manifest decoding to it.
4. **`CaptureRequest` is more permissive than the prose contract**: the real
   schema accepts metadata/quality fields flattened at the top level (with
   some renamed, e.g. `exposure_duration` vs. `exposure_duration_seconds`) as
   an alternative to the nested `{metadata, quality}` shape the app already
   sends. The nested shape the app uses appears to remain valid either way —
   no client change expected here, just noted for whoever reviews the
   generated request type.
5. **Manifest schema coverage looks thin**: `OpenApiSpex`'s `Manifest`
   schema only requires `schema_version`, `sheet_id`, and `capture_profile`
   (itself only requiring `scoring_algorithm_version`). The rich nested
   structure the iOS app actually consumes — `page`, `registration_markers`,
   `patches`, `pairs`, full `printer_profile` — may not be strictly typed in
   the spec yet. If confirmed, this is the main risk to the issue's stated
   dependency ("spec must ... cover the sheet/capture endpoints"): the
   generator may produce a `Manifest` type far less specific than
   `MeasurementCore.SheetManifest`, requiring either a spec fix upstream or
   hand-written decoding to stay for the nested fields.
6. **`RankedResults` schema looks minimal** (`schema_version`, `sheet_id`
   only) versus the prose contract's description (source colors, scores,
   labels, capture provenance, printer profile, scoring algorithm version).
   Needs direct confirmation — likely the same truncation/coverage risk as
   (5), or the summarization tool simply didn't surface the rest of the
   fields.
