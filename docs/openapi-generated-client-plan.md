# Generated OpenAPI client migration plan (issue #5)

Test-writing run for replacing the hand-written API layer with a client
generated by `swift-openapi-generator` from the spec published by
viamin/color_matching#110.

## Verification plan (acceptance criterion → smallest credible verification)

| Criterion | Verification | Home |
| --- | --- | --- |
| Generator + runtime added; OpenAPI document vendored | Focused unit tests asserting the vendored document exists, parses as OpenAPI 3, and pins every app surface (paths, path params, bearer auth, required response fields, compatibility enums) | `iOS/Tests/ColorMatchingLPSAppTests/OpenAPIDocumentTests.swift` |
| Client generated for the surfaces the app uses today | Focused unit tests asserting `iOS/Package.swift` wires the `OpenAPIGenerator` plugin and `OpenAPIRuntime` into a `GeneratedAPIClient` target, and that `ColorMatchingLPSAppCore` depends on it | `iOS/Tests/ColorMatchingLPSAppTests/OpenAPIPackageWiringTests.swift` |
| Hand-written API models replaced by generated types; client-side models stay | Wiring assertion above (app core consumes `GeneratedAPIClient`) plus the stubbed-response suite below exercising generated `Components.Schemas.*` types end to end | same file + stubbed suite |
| Swift tests exercising the generated client against local stubbed responses | `ClientTransport`-level stubbed-response suite: six operations (recent sheets, manifest, create capture, upload measurements, upload judgments, ranked results) plus a documented-404 case; asserts wire paths, payloads and decoded fields; no live server | `iOS/Tests/GeneratedClientTests/GeneratedClientStubbedResponseTests.swift` |
| PR description records contract deltas and endpoint gaps | Delta table below is the PR-body source; deltas are additionally pinned by the document tests so regeneration surfaces drift | this file + `OpenAPIDocumentTests` |

The stubbed-response suite lives under `iOS/Tests/GeneratedClientTests/` and is
inert until `iOS/Package.swift` declares the `GeneratedClientTests` test target
(the wiring test fails red until then, so it cannot be silently skipped).

## How the spec is published and vendored

`color_matching` builds its spec with OpenApiSpex from the router and
controller specs (`lib/color_matching_web/api_spec.ex`) and serves it,
unauthenticated, at:

```http
GET /api/v1/openapi.json
```

Vendor it verbatim (no hand edits — server-side drift must stay visible as a
regeneration diff):

```bash
curl -sS http://localhost:4000/api/v1/openapi.json \
  > iOS/OpenAPI/color-matching-openapi.json
```

(`mix openapi.spec.json` from the Phoenix app is an equivalent source.)
swift-openapi-generator consumes JSON documents directly.

## Agreed integration contract

- Vendored document: `iOS/OpenAPI/color-matching-openapi.json` (JSON, not
  YAML, so the test suite can parse it with `JSONSerialization` and no extra
  dependencies).
- Generated client target: `GeneratedAPIClient`, built by the
  `OpenAPIGenerator` plugin, linking `OpenAPIRuntime`.
- `ColorMatchingLPSAppCore` depends on `GeneratedAPIClient`.
- Test target `GeneratedClientTests` depends on `GeneratedAPIClient` and
  compiles `iOS/Tests/GeneratedClientTests/*.swift`.
- Generated method names come from swift-openapi-generator's idiomatic
  mangling of the published operationIds
  (`ColorMatchingWeb.TestSheetController.manifest` →
  `colorMatchingWebTestSheetControllerManifest`, etc.). If a regenerated
  client spells a call differently, rename the call sites in the stubbed
  suite mechanically — the wire-level assertions (paths, JSON payloads,
  decoded fields) are the contract and must not change.

## Contract deltas: prose contract vs published spec

Prose source: `docs/color-matching-api-contract.md`. Spec source: the schemas
declared in `color_matching` `lib/color_matching_web/api_schemas.ex` as served
by `/api/v1/openapi.json`.

1. **Upload responses have bodies and status 200.** The prose contract
   documents no response for measurement/judgment upload (the app's
   hand-written client treated them as fire-and-forget and its tests stubbed
   `204`). The published spec answers `200 OK` with JSON:
   `MeasurementUploadResponse` requires `capture_id`, `measurement_count`,
   `pair_score_count`; `JudgmentUploadResponse` requires `capture_id`,
   `judgment_count`. The generated client surfaces these as decoded types.
2. **`normalized_linear_rgb_median` is required** on every measurement in the
   spec; the prose contract and the app's `PatchMeasurement` treat it as
   optional. The app must always send it (today the analyzer produces it
   whenever normalization runs).
3. **No `stats` block and no top-level `scoring_algorithm_version`** in the
   published `MeasurementUploadRequest`. The prose contract (and the current
   app upload payload) include `stats` (`sample_count`, `clipping_fraction`,
   `mean`, `standard_deviation`) and `scoring_algorithm_version`. OpenApiSpex
   does not reject unspecified fields at runtime by default, but they are
   outside the contract: the app should stop sending them or the server spec
   should grow them (follow-up on color_matching).
4. **RGB payloads are polymorphic.** The spec declares `RgbPayload` as
   anyOf(array of numbers | `{r,g,b}` object | string). The prose contract
   only documents the object form, which is what the app sends and asserts.
5. **`iso` is an integer** in the spec; the hand-written `CaptureMetadata`
   uses `Float`. Generated types use `Int`; fractional ISO values will be a
   compile-time-visible change.
6. **`white_balance_gains` is an opaque object** in the spec (no `red/green/
   blue` properties), unlike the prose contract's typed gains object.
7. **Capture request accepts a flat compatibility shape too.** Besides the
   app's nested `metadata` + `quality` form, `CaptureRequest` also allows
   flattened fields (`exposure_duration`, `rejection_reasons`, etc.) via
   anyOf. The app keeps using the nested form.
8. **No rejection or judgment enums.** The prose contract enumerates allowed
   capture rejections and judgments (`match`/`near_match`/`no_match`); the
   spec types both as plain strings.
9. **Auth matches:** `bearerAuth` (HTTP bearer) security scheme, declared on
   the sheet/capture operations.

## Endpoint gaps discovered (spec does not yet cover what the app needs)

- **Manifest payloads are mostly unspecified.** The published
  `TestSheetManifest` only defines `schema_version`, `sheet_id`, and
  `capture_profile.scoring_algorithm_version`. The prose contract (and the
  app's `SheetManifest` model in `MeasurementCore`) rely on `sheet_version`,
  `manifest_url`, `created_at`, `page`, `registration_markers`,
  `printer_profile`, `patches`, and `pairs`. Extra fields are ignored by
  generated decoders, so switching manifest decoding to generated types would
  silently drop everything the sheet analyzer needs. Until color_matching
  expands the manifest schema (follow-up issue needed there), manifest
  consumption beyond the three pinned fields must stay on the client-side
  model.
- **Ranked results are unspecified beyond identity fields.** The published
  `RankedResults` schema requires only `schema_version`
  (`lps-ranked-results/v1`) and `sheet_id`; the prose contract promises source
  colors, scores, labels, capture provenance, printer profile, and scoring
  algorithm version. Same follow-up needed before the app can consume ranked
  results through generated types.

## Environment notes

- The authoring container for this run has no Swift toolchain, so `swift test`
  could not be executed locally. The two suites under
  `iOS/Tests/ColorMatchingLPSAppTests/` compile with Foundation + XCTest only
  and fail red on the missing vendored document and missing package wiring
  (the intended red-phase evidence); CI (macos runner) runs `swift test` on
  the PR.
- Exit criterion for the implementation run: `swift test --disable-sandbox`
  green in `iOS/` with the generated types wired in, including
  `GeneratedClientTests`.
