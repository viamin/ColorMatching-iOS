# Generated OpenAPI Client Adoption Plan (issue #5)

Status: **test-writing phase (red)**. This document is the implementation
contract for the follow-up implementation run: the tests committed alongside it
define the target behavior; this file pins the naming and layout decisions those
tests assume. No implementation files were changed in this phase.

Upstream dependency: [viamin/color_matching#110](https://github.com/viamin/color_matching/issues/110)
(closed; the spec ships with the Phoenix app and is served at `GET /api/v1/openapi.json`).

## What changes

Replace the hand-written API layer (`iOS/Sources/ColorMatchingLPSAppCore/APIClient.swift`
Codable models + hand-built `URLRequest`s) with a client generated by
[swift-openapi-generator](https://github.com/apple/swift-openapi-generator) from
the published OpenAPI document, so server-side drift becomes a regeneration diff
or compile error instead of a runtime surprise.

## Package layout (naming contract)

The committed tests assume exactly these names:

| What | Value |
| --- | --- |
| Generated target / module name | `ColorMatchingOpenAPI` |

### Why verbatim vendoring

The spec's `operationId`s are generated by `open_api_spex` as
`"#{inspect(controller)}.#{action}"` (e.g. `ColorMatchingWeb.TestSheetController.manifest`).
`swift-openapi-generator` maps them to Swift method names via its
`IdiomaticSafeNameGenerator` (periods become underscores, first word lowercased).
Vendoring the document byte-for-byte (no local operationId rewrites) keeps the
drift story honest: an upstream rename shows up as a compile error at exactly
the call sites named below.

Derived method names the tests call (all verified against the generator's
naming algorithm; see `docs/contract-deltas-prose-vs-openapi.md` for the source
operationIds):

| Operation | operationId (vendored, verbatim) | Generated method |
| --- | --- | --- |
| GET `/api/v1/test_sheets/recent` | `ColorMatchingWeb.TestSheetController.recent` | `colorMatchingWeb_TestSheetController_recent` |
| GET `/api/v1/test_sheets/{sheet_id}/manifest` | `ColorMatchingWeb.TestSheetController.manifest` | `colorMatchingWeb_TestSheetController_manifest` |
| GET `/api/v1/test_sheets/{sheet_id}/ranked_results` | `ColorMatchingWeb.TestSheetController.ranked_results` | `colorMatchingWeb_TestSheetController_ranked_results` |
| POST `/api/v1/test_sheets/{sheet_id}/captures` | `ColorMatchingWeb.CaptureController.create` | `colorMatchingWeb_CaptureController_create` |
| POST `/api/v1/captures/{capture_id}/measurements` | `ColorMatchingWeb.CaptureController.upload_measurements` | `colorMatchingWeb_CaptureController_upload_measurements` |
| POST `/api/v1/captures/{capture_id}/judgments` | `ColorMatchingWeb.CaptureController.upload_judgments` | `colorMatchingWeb_CaptureController_upload_judgments` |

### Vendoring source

There is no public deployment of the Phoenix app, so the document cannot be
fetched over HTTP from CI. `docs/openapi-vendoring-source.json` is a faithful
reconstruction of `ColorMatchingWeb.ApiSpec.spec()` from the upstream sources
(`api_spec.ex`, `api_schemas.ex`, `router.ex`, and the five controllers, at
upstream HEAD as of 2026-10-31). When vendoring:

1. Prefer re-rendering from a running instance (`mix phx.server` then
   `curl localhost:4000/api/v1/openapi.json`), and diff against
   `docs/openapi-vendoring-source.json` — differences beyond key ordering are
   upstream drift and belong in the PR description.
2. If no instance is available, `docs/openapi-vendoring-source.json` is the
   reviewed fallback: copy it to `iOS/Sources/ColorMatchingOpenAPI/openapi.json`.

## Known risks for the implementation run

- **`CaptureRequest` combines `type: object` with a sibling `anyOf`** (open_api_spex
  emits the flat-form compatibility union that way). If the pinned generator
  version rejects that combination, raise it upstream rather than editing the
  vendored document locally; a local edit would silently weaken drift detection.
- **The published `TestSheetManifest`/`RankedResults` schemas are thinner than
  the payloads the server actually renders** (see the deltas doc). The generated
  manifest type carries only `schema_version`, `sheet_id`, and
  `capture_profile.scoring_algorithm_version` — `MeasurementCore`'s analyzer
  needs `patches` and `pairs`. Options, in preference order:
  1. Extend the upstream spec to declare the full manifest (best; keeps a
     single source of truth) — file the upstream issue in the implementation PR.
  2. Until then, keep the full-manifest decoding in `ColorMatchingLPSAppCore`
     for the undeclared fields and use the generated client for everything else,
     with the gap recorded in the PR description.
- **Upload responses now carry bodies** (200 + counts, not 204-tolerant
  fire-and-forget): the facade must surface `measurement_count` /
  `pair_score_count` / `judgment_count` or at minimum not treat them as errors.
- **Per-score `algorithm_version`** replaces the prose top-level
  `scoring_algorithm_version`; `LPSScorer.algorithmVersion` moves into each
  score payload.
