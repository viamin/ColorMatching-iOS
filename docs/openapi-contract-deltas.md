# Contract Deltas: Prose Contract vs. Published OpenAPI Spec

This records what was found while preparing to replace the hand-written
`/api/v1` API layer (`ColorMatchingLPSAppCore/APIClient.swift`) with a client
generated by `swift-openapi-generator`, per
[viamin/ColorMatching-iOS#5](https://github.com/viamin/ColorMatching-iOS/issues/5).

The dependency, [viamin/color_matching#110](https://github.com/viamin/color_matching/issues/110),
is closed and merged as
[viamin/color_matching#113](https://github.com/viamin/color_matching/pull/113)
(merge commit `094bd6d3443ddacbda7e63354299867eb5bdfa9f`). No live `color_matching`
server is reachable from this sandbox or from CI, so the comparison below was
built by reading the merged source directly:

- `lib/color_matching_web/api_spec.ex`, `lib/color_matching_web/api_schemas.ex`
  — the `OpenApiSpex` schema definitions that back the generated document.
- `lib/color_matching_web/router.ex` — the actual route table.
- `lib/color_matching_web/controllers/capture_controller.ex`,
  `test_sheet_controller.ex`, `test_sheet_json.ex` — the real
  request/response bodies the formal schemas sometimes under-document.

**Important implementation note for the next (non-test) run:** the spec is
not a static file in `color_matching`. It is rendered at request time by
`ColorMatchingWeb.OpenApiController` at `GET /api/v1/openapi.json`
(`ColorMatchingWeb.ApiSpec.spec/0` derives it from `Router.__routes__/0`).
There is nothing to `git fetch` from the `color_matching` repo as a checked-in
file. "Fetch or vendor" therefore means: hit a running instance's
`/api/v1/openapi.json` once and commit the resulting JSON as a vendored
snapshot in this repo (so `swift-openapi-generator` and CI never need a live
server), with a documented process for refreshing that snapshot when
`color_matching` changes its routes/schemas.

## Deltas found

### 1. Manifest (`GET /api/v1/test_sheets/:sheet_id/manifest`)

The prose contract and the real response (`TestSheetJSON.manifest/1`) agree
closely on `schema_version`, `sheet_id`, `sheet_version`, `manifest_url`,
`page`, `registration_markers`, `patches`, and `pairs`.

Two confirmed gaps:

- **The published OpenAPI schema (`ApiSchemas.Manifest`) only formally
  declares three properties**: `schema_version`, `sheet_id`, and
  `capture_profile.scoring_algorithm_version`. It does not declare `page`,
  `registration_markers`, `patches`, `pairs`, `sheet_version`,
  `manifest_url`, `created_at`, or `printer_profile`, even though the real
  controller always returns all of them. A client generated strictly from
  the published schema would therefore need a hand-authored, richer schema
  (or the `color_matching` spec needs to be fleshed out) to get typed access
  to `patches`/`pairs`, which this app cannot function without. This is a
  genuine OpenAPI-spec completeness gap, not just a prose-vs-code
  difference.
- **`printer_profile` field names differ from the prose contract's
  example.** The prose contract shows `id`, `name`, `paper`, `ink`,
  `settings`. The real response (`TestSheetJSON.render_printer_profile/1`)
  sends `printer_make_model`, `paper_type`, `ink_type`, `icc_profile`,
  `print_settings`, `driver_name`, `driver_version`, `calibration_date`,
  `calibration_version`, `notes` — no `id`, `name`, or bare `settings` key.
  The current hand-written `SheetManifest` Swift model has no
  `printer_profile` or `capture_profile` property at all, so this payload is
  silently dropped today. `iOS/Tests/ColorMatchingLPSAppTests/OpenAPIContractDeltaTests.swift`
  (`testManifestDecodeDropsPrinterProfileAndCaptureProfileFromRealAPIResponse`)
  pins this down as a failing test against a fixture built from the real
  `TestSheetJSON.manifest/1` shape.
- `capture_profile.scoring_algorithm_version` is exactly what this app needs
  to compare against `LPSScorer.algorithmVersion` to detect server-side
  scoring drift (the whole motivation for this issue), but the hand-written
  model cannot see it today because `capture_profile` isn't decoded at all.

### 2. Recent sheets (`GET /api/v1/test_sheets/recent`)

Matches the prose contract and the app's `RecentSheet` model. One
behavioral note: `TestSheetJSON.render_recent_sheet/1` currently hardcodes
`title: nil` unconditionally — the prose contract's example
(`"July LPS comparison sheet"`) is aspirational, not yet implemented
server-side. Not a client-side defect (the model already treats `title` as
optional), just worth knowing before relying on it.

### 3. Create capture session (`POST /api/v1/test_sheets/:sheet_id/captures`)

The published `CaptureRequest` schema accepts two shapes via `anyOf`: a flat
top-level set of fields, or a nested `{metadata, quality}` object. The app
already sends the nested form, which is one of the two valid shapes — no
change needed here. `quality.detected_marker_count` / `blur_score` /
`rejections` line up with `CaptureQuality`. `CaptureMetadata.iso` is typed
`integer` in the published schema vs. `Float?` in the Swift model; this does
not cause a decode failure (JSON numeric literals decode into `Float` fine),
but the generated client should match the server's `Int` typing.

### 4. Upload measurements (`POST /api/v1/captures/:capture_id/measurements`)

Two confirmed gaps, both demonstrated by failing tests in
`OpenAPIContractDeltaTests.swift`:

- **The hand-written client sends fields the published
  `MeasurementUploadRequest` schema does not declare.** The schema's only
  top-level properties are `measurements` and `pair_scores`
  (`ApiSchemas.MeasurementUploadRequest`). The current
  `APIClient.uploadMeasurements` always adds a top-level
  `scoring_algorithm_version` key that has no counterpart in the published
  schema. Each measurement item's schema only declares `patch_id`,
  `linear_rgb_median`, and `normalized_linear_rgb_median` — the client also
  sends a `stats` object (`sample_count`, `clipping_fraction`, `mean`,
  `standard_deviation`) that isn't part of the published contract. The
  server likely ignores unrecognized keys rather than rejecting them, but a
  client generated from the real spec would not have a way to send `stats`
  or `scoring_algorithm_version` at this level at all, so this app-level
  data (useful for debugging/telemetry) would need a different home, or the
  `color_matching` spec needs to be extended to accept it deliberately.
- **The response body is real and is discarded today.**
  `CaptureController.handle_measurement_upload/3` returns HTTP 200 (not 204)
  with `{"capture_id": ..., "measurement_count": ..., "pair_score_count":
  ...}`. `APIClient.uploadMeasurements` returns `Void` and never looks at
  the response body, so the app has no way to confirm what the server
  actually persisted. The generated client should surface
  `MeasurementUploadResponse` to its caller.

### 5. Upload judgments (`POST /api/v1/captures/:capture_id/judgments`)

The request body the client sends (`{"judgments": [{"pair_id", "judgment"}]}`)
matches the published `JudgmentUploadRequest` schema exactly — no delta on
the request side. One gap on the response side, mirroring measurements:
`CaptureController.handle_judgment_upload/3` returns HTTP 200 with
`{"capture_id": ..., "judgment_count": ...}`, which `APIClient.uploadJudgments`
(also `Void`-returning) discards.

One notable looseness: the prose contract documents an enumerated set of
valid `judgment` values (`match` / `near_match` / `no_match`), but the
*published* schema types `judgment` as a bare `string` with no `enum`
constraint. A client generated from the real spec will not gain compile-time
or decode-time validation of judgment values — the enum constraint exists
only in the prose doc, not in the machine-readable contract. The same is
true for capture `rejection_reasons` / `quality.rejections`: the prose
contract's enumerated rejection reasons have no `enum` in the published
schema either. (This app already encodes those as a client-side
`CaptureRejection` Swift enum for its own scoring logic, which is a
purely client-side concern per this issue's non-goals and should stay as
hand-written.)

### 6. Ranked results (`GET /api/v1/test_sheets/:sheet_id/ranked_results`)

**This app has no client code for this endpoint today** — no method on
`APIClient`, no Swift model. This is an outright gap relative to the
issue's deliverable list, which names ranked results as one of the surfaces
to cover.

The published OpenAPI schema (`ApiSchemas.RankedResults`) is very thin: only
`schema_version` and `sheet_id` are declared. The *real* response
(`TestSheetJSON.ranked_results/1`) is much richer:

```jsonc
{
  "schema_version": "lps-ranked-results/v1",
  "sheet_id": "...",
  "printer_profile": { /* same shape as the manifest's printer_profile */ },
  "capture_count": 0,
  "latest_capture_at": "2026-...Z",
  "earliest_capture_at": "2026-...Z",
  "scoring_algorithm_versions": ["lps-distance-v1"],
  "results": [
    {
      "rank": 1,
      "pair_id": "pair_1",
      "scoring_algorithm_version": "lps-distance-v1",
      "row": 0,
      "col": 1,
      "source_colors": {"color_a_hex": "#FF0000", "color_b_hex": "#00FF00"},
      "score": {
        "average": 0.1, "latest": 0.1, "minimum": 0.1, "maximum": 0.1,
        "capture_count": 1, "sample_count": 1, "algorithm_versions": ["lps-distance-v1"]
      },
      "current_judgment": "near_match",
      "current_judgment_observed_at": "2026-...Z",
      "observation_count": 1,
      "latest_observation": {"judgment": "near_match", "observed_at": "2026-...Z"},
      "capture_count": 1,
      "latest_capture_at": "2026-...Z",
      "earliest_capture_at": "2026-...Z"
    }
  ]
}
```

This is a bigger documented gap than the prose contract's one-line
description ("source colors, scores, labels, capture provenance, printer
profile, and scoring algorithm version") suggests, and a bigger one than the
published OpenAPI schema captures. Like the manifest, the
`color_matching`-side OpenAPI schema for this endpoint needs to be filled
out before a generated client gets a usable `RankedResults` type; until
then, generation would need a hand-maintained schema override for this
response. A fixture test
(`testRankedResultsRealResponseShapeDecodesForFutureGeneratedClient` in
`OpenAPIContractDeltaTests.swift`) pins the real shape above down with a
test-local decodable type, to give the next (implementation) run a verified
target instead of re-deriving it from `color_matching` source again.

## Summary for the implementation run

1. Vendor a snapshot of `GET /api/v1/openapi.json` from a running
   `color_matching` instance (there is no static spec file to fetch).
2. Expect the vendored spec's `Manifest` and `RankedResults` schemas to be
   thinner than what this app actually needs; either get `color_matching` to
   flesh them out first, or carry a local OpenAPI schema override/patch
   until it does.
3. Drop `scoring_algorithm_version` and `stats` from the outgoing
   measurement-upload payload (or get `color_matching` to formally accept
   them) — they're not part of the published `MeasurementUploadRequest`
   schema.
4. Surface `MeasurementUploadResponse` / `JudgmentUploadResponse` to callers
   instead of discarding them.
5. Add the ranked-results surface, which does not exist in this app at all
   today.
6. Do not expect enum-level compile-time safety on `judgment` or
   `rejection_reasons` from the generated client — the published schema
   types both as unconstrained strings.
