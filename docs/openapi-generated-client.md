# Generated OpenAPI Client Plan (issue #5, tests-first run)

Status: **red-phase test plan.** The tests committed alongside this document specify the
behavior the implementation run must deliver: a Swift client generated by
[`swift-openapi-generator`](https://github.com/apple/swift-openapi-generator) from the
OpenAPI document published by `viamin/color_matching` (issue
[viamin/color_matching#110](https://github.com/viamin/color_matching/issues/110), shipped in
PR [#113](https://github.com/viamin/color_matching/pull/113), spec served at
`GET /api/v1/openapi.json`).

This document also records the deltas found between the prose contract
(`docs/color-matching-api-contract.md`) and the published spec — the PR description for the
implementation run should carry the same delta table.

## Required package wiring (implementation run)

- New target `ColorMatchingOpenAPI` (library) with:
  - `openapi.json` vendored at `iOS/Sources/ColorMatchingOpenAPI/openapi.json`, fetched from
    the Phoenix app's `GET /api/v1/openapi.json` (do not hand-edit the fetch result; any
    normalization must be scripted and recorded).
  - `openapi-generator-config.yaml` with `generate: [types, client]`, `access: public`,
    and `namingStrategy: idiomatic` (the default `defensive` strategy mangles the dotted
    operationIds into names like `ColorMatchingWeb_period_TestSheetController_period_manifest`;
    the idiomatic strategy is the reviewable choice used by the tests below).
  - The `OpenAPIGenerator` plugin from `swift-openapi-generator`.
  - Dependencies: `swift-openapi-runtime`; the app target additionally uses
    `swift-openapi-urlsession-runtime` (`URLSessionTransport`).
- The vendored document is committed so regeneration diffs are reviewable; refreshing it is a
  one-command `curl` documented in the target's README or the PR description.

### Why these names

The served spec is produced with `open_api_spex`, whose default operationIds are
`"<ControllerModule>.<action>"` (`OpenApiSpex.OperationBuilder.build_operation_id/3`).
With `namingStrategy: idiomatic` (SOAR-0013: first word lowercased, `.` → `_` within a
word, `_` treated as a word separator) the generated `Client` methods are:

| Operation (spec)                                                 | Swift method                                            |
| ---------------------------------------------------------------- | ------------------------------------------------------- |
| `ColorMatchingWeb.TestSheetController.recent`                    | `colorMatchingWeb_TestSheetController_recent`           |
| `ColorMatchingWeb.TestSheetController.manifest`                  | `colorMatchingWeb_TestSheetController_manifest`         |
| `ColorMatchingWeb.TestSheetController.ranked_results`            | `colorMatchingWeb_TestSheetController_rankedResults`    |
| `ColorMatchingWeb.CaptureController.create`                      | `colorMatchingWeb_CaptureController_create`             |
| `ColorMatchingWeb.CaptureController.upload_measurements`         | `colorMatchingWeb_CaptureController_uploadMeasurements` |
| `ColorMatchingWeb.CaptureController.upload_judgments`            | `colorMatchingWeb_CaptureController_uploadJudgments`    |

Keeping the raw spec operationIds (no rewriting during vendoring) is deliberate: a future
rename upstream then shows up as a compile error here instead of being masked by a local
rewrite script.

## Contract deltas: prose contract vs published spec

All statements verified against `viamin/color_matching@main`: `lib/color_matching_web/api_spec.ex`,
`lib/color_matching_web/api_schemas.ex`, `lib/color_matching_web/router.ex`,
`lib/color_matching_web/controllers/test_sheet_controller.ex`,
`lib/color_matching_web/controllers/capture_controller.ex`.

1. **Sheet manifest is only partially typed.** The published `TestSheetManifest` schema types
   only `schema_version` (enum `lps-sheet-manifest/v1`), `sheet_id`, and
   `capture_profile.scoring_algorithm_version` (enum `lps-distance-v1`). The prose contract's
   `sheet_version`, `manifest_url`, `created_at`, `page`, `registration_markers`,
   `printer_profile`, `patches`, and `pairs` are **absent from the schema** (allowed at
   runtime by unspecified `additionalProperties`, but dropped by the generated Codable).
   The iOS app's `SheetAnalyzer` needs `patches`/`pairs`, so this is an **endpoint gap**:
   the manifest schema needs upstream enrichment before the app can rely on generated types
   for the full manifest. Until then the client-side `SheetManifest` model stays (it is
   decode-only and does not duplicate any upload surface).
2. **Capture creation body has two accepted shapes.** The prose contract sends nested
   `{metadata, quality}`. The published `CaptureRequest` accepts that nested form (via its
   `anyOf` branch requiring `metadata`) but also a flat form, and the two forms disagree on
   names: flat `exposure_duration` vs nested `exposure_duration_seconds`; flat
   `rejection_reasons` vs nested `quality.rejections`. The app should keep sending the
   nested prose shape. Note: `CaptureRequest` and `PairScoreRequest` declare `properties`
   and `anyOf` as siblings, which OpenAPI 3 ignores/merges ambiguously — if the generator
   drops the sibling properties, normalize the vendored copy (scripted, recorded) and file an
   upstream follow-up.
3. **Measurement upload lost fields.** The published `MeasurementUploadRequest` has no
   top-level `scoring_algorithm_version` (prose had it), no per-measurement `stats` block
   (`sample_count`, `clipping_fraction`, `mean`, `standard_deviation` all absent), and makes
   `normalized_linear_rgb_median` **required** (optional in prose). RGB values are a loose
   `RgbPayload` `anyOf` of array / `{r,g,b}` object / string.
4. **Measurement upload now returns a body.** `200` with `MeasurementUploadResponse`
   `{capture_id, measurement_count, pair_score_count}`; the prose contract specified no
   response body. Harmless for the app (it ignores upload bodies today).
5. **Judgment upload now returns a body** `{capture_id, judgment_count}`, and `judgment`
   values are not enum-constrained in the spec (prose lists `match` / `near_match` /
   `no_match`).
6. **Ranked results are only partially typed.** `RankedResults` types only `schema_version`
   (new enum `lps-ranked-results/v1` — **new value, not in the prose contract**) and
   `sheet_id`. The prose promise of "source colors, scores, labels, capture provenance,
   printer profile, and scoring algorithm version" is untyped. Second **endpoint gap**,
   lower priority (the iOS app does not consume ranked results yet).
7. **Recent sheets match** the prose shape exactly (`sheets[]` with `sheet_id`,
   `manifest_url`, nullable `title`); `manifest_url` is a plain string, not `format: uri`.
8. **Auth matches**: `components.securitySchemes.bearerAuth` is `http`/`bearer`; development
   may still allow anonymous requests.
9. **Extra endpoints exist in the spec** that the iOS app does not use (`printer_profiles`,
   `palettes`, `colors`, `metamer_pairs`, `illuminant_measurements`, `multi_image_mapping`).
   They will appear in the generated client; the app simply must not call them (non-goal to
   remove them from generation).
10. **No missing endpoints**: all six paths the app uses today exist in the published spec
    with the methods and path parameters expected.

## Test assumptions the implementation run may need to adjust

- Module name `ColorMatchingOpenAPI`; vendor path
  `iOS/Sources/ColorMatchingOpenAPI/openapi.json`.
- `openapi-generator-config.yaml` sets `namingStrategy: idiomatic`; generated method names
  follow the table above (`swift-openapi-generator` ≥ 1.6, which introduced the
  `namingStrategy` config key).
- Request payloads in tests are built by decoding canned wire JSON with a plain
  `JSONDecoder` (iso8601 dates), so generated memberwise-init parameter order does not
  matter; only the wire keys do.
- `ClientTransport` stub uses the `send(_:body:baseURL:operationID:)` signature from
  `swift-openapi-runtime` ≥ 1.5.
- Bearer auth is applied with a `ClientMiddleware` (documented runtime pattern) and asserted
  at the transport, so the tests do not depend on generated `Input.Security` details.
- The Xcode project (`ColorMatchingLPS.xcodeproj`) enumerates source files explicitly; add
  the new test files to the `ColorMatchingLPSAppTests` target (and the generated framework
  to the app target) when the package wiring lands, so the `xcodebuild` simulator job runs
  them too. `swift test` picks them up automatically.
