# Generated OpenAPI Client Migration Plan (issue #5)

Status: **test-writing phase**. The tests referenced here are committed and
intentionally red until the implementation run lands the generated client.
This document is the implementation contract for that run and the source for
the PR description's contract-delta section.

## Goal

Replace the hand-written API layer (`iOS/Sources/ColorMatchingLPSAppCore/APIClient.swift`)
with a typed client generated by `swift-openapi-generator` from the OpenAPI 3
document published by `viamin/color_matching` (upstream issue
viamin/color_matching#110, landed as viamin/color_matching#113, spec served at
`GET /api/v1/openapi.json`). Server-side drift then becomes a regeneration
diff or compile error instead of a runtime surprise.

## Implementation contract for the implementation run

These details are pinned by the committed tests; deviating from them requires
changing the tests.

### Package layout

The `OpenAPIGenerator` **build plugin does not read the plugin
`configuration:` dictionary**. It looks for two files inside the *generated
target's* sources (`Plugins/PluginsShared/PluginUtils.swift` in
swift-openapi-generator):

- exactly one document named `openapi.json` (or `openapi.yaml`/`openapi.yml`),
- exactly one config named `openapi-generator-config.yaml` (or `.yml`).

So the target and its files must look like this:

```
iOS/Sources/ColorMatchingOpenAPI/
  openapi.json                     # vendored snapshot of GET /api/v1/openapi.json
  openapi-generator-config.yaml    # generate/accessModifier/namingStrategy
```

`iOS/Package.swift` gains:

```swift
dependencies: [
    .package(url: "https://github.com/apple/swift-openapi-generator", from: "1.14.0"),
    .package(url: "https://github.com/apple/swift-openapi-runtime", from: "1.13.0"),
],
```

```swift
.target(
    name: "ColorMatchingOpenAPI",
    dependencies: [.product(name: "OpenAPIRuntime", package: "swift-openapi-runtime")],
    plugins: [.plugin(name: "OpenAPIGenerator", package: "swift-openapi-generator")]
),
```

`ColorMatchingLPSAppCore` depends on `ColorMatchingOpenAPI` **and**
`OpenAPIRuntime` (the bearer middleware lives there); the test target
`ColorMatchingLPSAppTests` depends on `ColorMatchingOpenAPI` and
`OpenAPIRuntime` — the `#if canImport` gates in the new tests only activate
once both are resolvable from the test target.

### Generator configuration (required, not optional)

```yaml
generate:
  - types
  - client
accessModifier: public
namingStrategy: idiomatic
```

Two settings are load-bearing:

- **`accessModifier: public`** — the generator's default is `internal`, which
  would make `Client` and `Components.Schemas.*` invisible to the app module
  and to the test module.
- **`namingStrategy: idiomatic`** — the default is `defensive`
  (`Config.defaultNamingStrategy`, SOAR-0001). The upstream operationIds
  contain dots (`ColorMatchingWeb.TestSheetController.manifest`), so the
  defensive strategy yields
  `colorMatchingWeb_period_TestSheetController_period_manifest` and keeps
  wire keys as Swift identifiers (`sheet_id` instead of `sheetId`). The
  idiomatic strategy (SOAR-0013) yields the names the tests pin.

### Authentication middleware

`swift-openapi-generator` does not translate OpenAPI security schemes into
generated code (see its `Supported-OpenAPI-features.md`: `security` and
`securitySchemes` are unchecked). The bearer token declared as `bearerAuth` in
the spec must be applied by a runtime middleware in `ColorMatchingLPSAppCore`,
contract pinned by `BearerAuthenticationMiddlewareTests`:

```swift
public struct BearerAuthenticationMiddleware: ClientMiddleware {
    public init(token: String)
    // intercept(...) sets "Authorization: Bearer <token>" on every outgoing
    // request, leaves all other headers intact, then calls next. A blank
    // token adds no header.
}
```

`APIClient` keeps its `token` API but uses the generated client + middleware
under the hood; its public wire behavior (bearer header, snake_case JSON,
paths, response decoding) is pinned by the existing `APIClientTests`, which
must remain green.

### Where the vendored document comes from

`GET /api/v1/openapi.json` on a running `color_matching` (the upstream test
`test/color_matching_web/controllers/open_api_controller_test.exs` pins the
published path set and the component schema names). Without a running
instance, the document can be reconstructed from the upstream sources, which
the upstream project serves verbatim:

- `lib/color_matching_web/api_schemas.ex` — component schemas (the schema
  `title` is the component key).
- `lib/color_matching_web/api_spec.ex` — `components.securitySchemes`.
- `lib/color_matching_web/router.ex` — paths and verbs.
- `lib/color_matching_web/controllers/test_sheet_controller.ex` and
  `controllers/capture_controller.ex` — operationIds, path parameters,
  response statuses and the controller-level `security` requirement.

### Required vendoring adjustments (codegen-driven)

OpenAPIKit (the parser `swift-openapi-generator` uses) reads a schema that
carries `anyOf` as a **pure union** and drops the sibling `properties` and
`required` keywords (`JSONSchema.init(from:)` returns early on `anyOf`;
`properties` live in `ObjectContext`, which is never decoded for a union).
Both upstream request schemas combine `anyOf` with `properties`, so two
adjustments to the vendored snapshot are required:

1. `CaptureRequest`: remove the `anyOf` keyword, keeping the documented
   `properties` (the flat legacy fields stay optional; the app keeps sending
   the nested `metadata` + `quality` shape).
2. `PairScoreRequest`: remove the `anyOf` keyword, keeping
   `pair_id`/`algorithm_version` required and `score`/`similarity`/`distance`
   optional.

Everything else stays verbatim. In particular `RgbPayload` (pure `anyOf`:
numeric array, `{r,g,b}` object, or JSON string) generates a proper enum and
must not be changed, and `white_balance_gains` (a bare `type: object`) maps to
`OpenAPIObjectContainer`, which the app may fill or leave `nil`. Both
adjustments must be called out in the PR description so upstream can either
accept them or restructure the schemas server-side.

### Generated names (derivation)

OperationIds come from upstream `OpenApiSpex` (`"<Module>.<action>"`, see
`OperationBuilder.build_operation_id`). `swift-openapi-generator` (SOAR-0013
idiomatic naming) maps them as follows — dots become underscores, `_` starts a
new camelCase word:

| OperationId (spec) | HTTP | Swift method on `Client` | Operations namespace type |
|---|---|---|---|
| `ColorMatchingWeb.TestSheetController.manifest` | GET `/api/v1/test_sheets/{sheet_id}/manifest` | `colorMatchingWeb_TestSheetController_manifest` | `Operations.ColorMatchingWeb_TestSheetController_manifest` |
| `ColorMatchingWeb.TestSheetController.recent` | GET `/api/v1/test_sheets/recent` | `colorMatchingWeb_TestSheetController_recent` | `Operations.ColorMatchingWeb_TestSheetController_recent` |
| `ColorMatchingWeb.TestSheetController.ranked_results` | GET `/api/v1/test_sheets/{sheet_id}/ranked_results` | `colorMatchingWeb_TestSheetController_rankedResults` | `Operations.ColorMatchingWeb_TestSheetController_rankedResults` |
| `ColorMatchingWeb.CaptureController.create` | POST `/api/v1/test_sheets/{sheet_id}/captures` | `colorMatchingWeb_CaptureController_create` | `Operations.ColorMatchingWeb_CaptureController_create` |
| `ColorMatchingWeb.CaptureController.upload_measurements` | POST `/api/v1/captures/{capture_id}/measurements` | `colorMatchingWeb_CaptureController_uploadMeasurements` | `Operations.ColorMatchingWeb_CaptureController_uploadMeasurements` |
| `ColorMatchingWeb.CaptureController.upload_judgments` | POST `/api/v1/captures/{capture_id}/judgments` | `colorMatchingWeb_CaptureController_uploadJudgments` | `Operations.ColorMatchingWeb_CaptureController_uploadJudgments` |

Generated schema types live under `Components.Schemas` keyed by the upstream
schema titles: `TestSheetManifest`, `RankedResults`, `RecentSheetsResponse`,
`CaptureMetadata`, `CaptureRequest`, `CaptureCreatedResponse`,
`MeasurementUploadRequest`, `MeasurementUploadResponse`,
`JudgmentUploadRequest`, `JudgmentUploadResponse`, `PairScoreRequest`,
`RgbPayload`, `ApiErrorResponse`. Wire keys stay snake_case (`sheet_id` →
`sheetId` etc.); string enums generate cases like
`TestSheetManifest.SchemaVersionPayload.lpsSheetManifestV1` (raw value
`lps-sheet-manifest/v1`) and
`TestSheetManifest.CaptureProfilePayload.ScoringAlgorithmVersionPayload.lpsDistanceV1`
(`lps-distance-v1`).

Naming rules worth knowing (they are why the tests avoid naming inline
types):

- An inline (anonymous) schema becomes a **nested** type whose name is the
  property name plus the `Payload` suffix
  (`Constants.Global.inlineTypeSuffix`): `CaptureRequest.quality` →
  `Components.Schemas.CaptureRequest.QualityPayload`, `schema_version` →
  `Components.Schemas.TestSheetManifest.SchemaVersionPayload`.
- Named component schemas keep their title: `Components.Schemas.CaptureMetadata`.
- Response cases follow the HTTP status: 200 `ok`, 201 `created`, 401
  `unauthorized`, 404 `notFound`, 422 `unprocessableContent`; anything else
  lands in `undocumented(statusCode:body:)`.
- `type: integer` → `Swift.Int`, `type: number` → `Swift.Double`,
  `format: date-time` → `Foundation.Date` (ISO-8601 on the wire).

If the generator rejects any other verbatim-spec construct, fix the vendored
copy minimally, record the adjustment in the PR description, and keep
`OpenAPISpecCoverageTests` green.

## Contract deltas: prose contract vs published spec

Comparison of `docs/color-matching-api-contract.md` (prose) against the
published spec sources (`lib/color_matching_web/api_schemas.ex`,
`api_spec.ex`, `router.ex`, controllers; viamin/color_matching#113). This
section is the basis for the PR description required by issue #5.

1. **Manifest schema is much thinner than the prose contract.** The published
   `TestSheetManifest` only documents `schema_version` (enum
   `lps-sheet-manifest/v1`), `sheet_id`, and
   `capture_profile.scoring_algorithm_version` (enum `lps-distance-v1`).
   The prose contract's `sheet_version`, `manifest_url`, `created_at`,
   `page`, `registration_markers`, `printer_profile`, `patches`, and `pairs`
   are not in the machine-readable schema. Consequence: the generated client
   cannot type the geometry the analyzer needs (`MeasurementCore.SheetManifest`
   stays a client-side decode of the undocumented extra fields). **Endpoint
   gap to file upstream**; tracked as the top follow-up.
2. **Capture request has two shapes (anyOf).** The published `CaptureRequest`
   accepts either a flat payload (where the exposure field is
   `exposure_duration`, not `exposure_duration_seconds` as in prose, and
   rejections are `rejection_reasons`) or the app's nested
   `metadata`/`quality` shape. The prose contract documents only the nested
   shape; the app should keep sending the nested one. Codegen note: OpenAPIKit
   drops sibling `properties` when `anyOf` is present, so the vendored copy
   removes the `anyOf` (see "Required vendoring adjustments") — same for
   `PairScoreRequest`.
3. **Measurement upload differs in four ways.** No top-level
   `scoring_algorithm_version` in the spec schema; no per-measurement `stats`
   block; `normalized_linear_rgb_median` is required (optional in prose); and
   RGB values are a `RgbPayload` anyOf (numeric array, `{r,g,b}` object, or
   JSON string) instead of a fixed `{r,g,b}` object. The app currently sends
   `scoring_algorithm_version` and `stats`, which the server tolerates
   (additional properties are allowed) but does not promise.
4. **Uploads return JSON bodies, not empty 204s.** The published spec declares
   200 responses with `MeasurementUploadResponse`
   (`capture_id`/`measurement_count`/`pair_score_count`) and
   `JudgmentUploadResponse` (`capture_id`/`judgment_count`). The prose
   contract showed no response body, and the hand-written tests used to stub
   `204` with an empty body — a real drift discovery; the stubs now answer
   `200` with the documented JSON shape.
5. **Pair scores require `algorithm_version` plus one of
   score/similarity/distance** (`PairScoreRequest` anyOf). The prose contract
   showed `distance` and `similarity` always present; the app's
   `lps-distance-v1` scorer can keep sending both.
6. **`capture_id` is a string-encoded integer** server-side
   (`Integer.to_string`), and path lookup is by sheet *lookup code*
   (`get_test_sheet_by_lookup_code`), not numeric sheet id.
7. **Authentication is machine-declared** as `securitySchemes.bearerAuth`
   (`http`/`bearer`) applied per-operation. The generator ignores security
   schemes, so the token must be attached by a client middleware (see above).
8. **Error shapes are machine-declared** (`ApiErrorResponse`, `errors` oneOf
   object/array) with 401/404/422 documented per operation, plus
   `undocumented` handling generated for anything else.
9. **Endpoints in the spec the app does not use today**:
   `/api/v1/printer_profiles*`, `/api/v1/palettes`, `/api/v1/colors`,
   `/api/v1/printer_profiles/{id}/metamer_pairs`, and the two previously
   undocumented `/api/illuminant_measurements(.bulk)` and
   `/api/multi_image_mapping` POST routes.
10. **Ranked results schema is a stub.** `RankedResults` documents only
    `schema_version` (enum `lps-ranked-results/v1`) and `sheet_id`; the prose
    contract promises source colors, scores, labels, capture provenance,
    printer profile, and scoring algorithm version. Second upstream gap to
    file; the app's local ranking stays authoritative until upstream fleshes
    this out.
