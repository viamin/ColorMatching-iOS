# Issue #5 OpenAPI Swift client verification plan

This is the tests-first plan for replacing the hand-written `/api/v1` client. It maps each issue acceptance criterion to its smallest credible verification before implementation begins.

| Criterion | Verification | Evidence at this head |
| --- | --- | --- |
| Generated client covers manifest and recent sheets | Permanent local-stub unit tests of the client boundary | `iOS/Tests/ColorMatchingLPSAppTests/APIClientTests.swift` (`testFetchManifestDecodesPublishedManifestFromLocalStub`, `testFetchRecentSheetsDecodesNullableTitleFromLocalStub`) |
| Generated client covers capture creation, measurements, and judgments | Permanent local-stub unit tests of request paths, auth, bodies, and published 200 response status | `iOS/Tests/ColorMatchingLPSAppTests/APIClientTests.swift` (`testCreateCaptureEncodesMetadataAndQuality`, `testUploadMeasurementsEncodesScoresWithAlgorithmVersion`, `testUploadJudgmentsEncodesPathAndPayload`) |

## Published-spec comparison

The comparison is against `viamin/color_matching` PR #113 (merged as `094bd6d3443ddacbda7e63354299867eb5bdfa9f`), which implements issue #110 and serves the specification at `GET /api/v1/openapi.json`.

- The route set matches the prose contract for manifest, recent sheets, capture creation, measurement upload, judgment upload, and ranked results.
- The published capture schema accepts both the nested `metadata`/`quality` request from the prose contract and a legacy flat request. Its nested metadata requirement is narrower than the prose example; the client should use the nested form.
- The published measurement schema requires `normalized_linear_rgb_median`; the prose contract presents that field but the current client-side model makes it optional. The implementation must decide how a missing normalization is represented before constructing the generated request.
- Published RGB measurement values accept an array, an `{r,g,b}` object, or a JSON string. The prose contract specifies only the object form; the generated client should send the object form used by the app today.
- The prose contract calls for a root `scoring_algorithm_version` and nested measurement `stats`; the published request schema does not require either. Keep the version only if the generated request type exposes it, and do not assume `stats` are contract-validated.
- The prose contract's upload examples imply empty successful responses, while the published spec documents JSON `200` responses for measurement and judgment upload. The tests use those published response statuses and envelopes.
- The prose lists closed sets of capture rejections and judgments, but the published schemas currently describe them as strings rather than enums. This is a server-spec precision gap.
- The prose asks ranked results to include source colors, scores, labels, provenance, printer profile, and algorithm version. The published `RankedResults` schema currently requires only `schema_version` and `sheet_id`. This is the blocking endpoint gap for a meaningful typed ranked-results UI model; preserve the app's current local ranking behavior until the server schema is expanded.
- The published manifest schema requires only `schema_version`, `sheet_id`, and `capture_profile`; the prose defines a richer manifest that the app decodes. The generated client migration must confirm which additional response fields are stable enough for app use.

## Implementation follow-up

Vendor a pinned `openapi.json` generated by the server, configure `swift-openapi-generator` to generate only the six endpoint surfaces, and replace `APIClient` transport/model decoding with a thin adapter over generated operations. Add the ranked-results local-stub test only once the server specifies its response fields. The existing fixture tests are intentionally local and do not require a live Phoenix server in CI.
