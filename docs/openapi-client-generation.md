# OpenAPI Client Generation Plan (iOS)

This document is the implementation contract for replacing the hand-written API layer
with a client generated by [swift-openapi-generator](https://github.com/apple/swift-openapi-generator).
It pins every name and path the tests depend on, so the implementation change set and
`iOS/Tests/ColorMatchingLPSAppTests/` stay in sync.

Source of truth for the server API: `viamin/color_matching` publishes an OpenAPI 3 spec at
`GET /api/v1/openapi.json` (landed in viamin/color_matching#110). The deltas between that
published spec and this repo's prose contract (`docs/color-matching-api-contract.md`) are
recorded in `docs/color-matching-api-contract-deltas.md`.

## Package layout

`iOS/Package.swift` gains:

- Products/dependencies:
  - `apple/swift-openapi-generator` (build tool plugin, 1.x)
  - `apple/swift-openapi-runtime` (product `OpenAPIRuntime`)
  - `apple/swift-openapi-urlsession` (product `OpenAPIURLSession`)
  - `apple/swift-http-types` (product `HTTPTypes`; needed directly by tests that build a transport wrapper)
- New target `ColorMatchingOpenAPI`:
  - sources: `iOS/Sources/ColorMatchingOpenAPI/`
  - contains `openapi.json` (or `openapi.yaml`) — the vendored document — plus
    `openapi-generator-config.yaml`:
    ```yaml
    generate:
      - types
      - client
    accessModifier: public
    namingStrategy: idiomatic
    ```
    Both keys matter: `public` so other targets/tests can use the generated types, and
    `idiomatic` so snake_case properties become Swift camelCase (`sheet_id` → `sheetId`);
    the default `defensive` strategy keeps raw names and the generated-client tests would
    not compile.
  - must also contain at least one `.swift` file (e.g. a placeholder comment file):
    SwiftPM drops targets whose directory has no Swift sources, in which case the
    OpenAPIGenerator build-tool plugin never runs and the target silently vanishes from
    the package graph (verified with SwiftPM 6.1 on Linux).
  - plugin: `.plugin(name: "OpenAPIGenerator", package: "swift-openapi-generator")`
- `ColorMatchingLPSAppCore` depends on `ColorMatchingOpenAPI`, `OpenAPIRuntime`, `OpenAPIURLSession`
- Test target `ColorMatchingLPSAppTests` gains dependencies on
  `ColorMatchingOpenAPI`, `OpenAPIRuntime`, `OpenAPIURLSession`, and `HTTPTypes`.

Validated toolchain pins for the implementation (a scratch Linux build generated the
client and compiled/ran `GeneratedClientStubbedServerTests` green against it):
swift-openapi-generator 1.13.1, swift-openapi-runtime 1.12.2,
swift-openapi-urlsession 1.4.0 (OpenAPIKit 6.4.0), Swift toolchain 6.1.

## Vendored OpenAPI document

- Path: `iOS/OpenAPI/color-matching-v1.json` (JSON, OpenAPI 3.0.x). The generator reads
  it from the generated target's source directory
  (`iOS/Sources/ColorMatchingOpenAPI/openapi.json` — either a copy or a symlink to the
  vendored document; a copy keeps Xcode projects happy).
- Origin: snapshot of `GET /api/v1/openapi.json` from `viamin/color_matching` (post #110).
- The snapshot is **normalized** for generator consumption. Every normalization is a pure
  naming/shape change with no wire-format effect and is listed below. Anything not listed
  must match the served spec byte-for-byte in structure so that re-vendoring a new served
  snapshot produces a reviewable diff.
- Component **property order matters**: generated initializers take arguments in property
  order (optionals defaulted), so keep properties ordered as in the served spec — the
  generated-client tests construct payloads in that order (e.g. `CaptureMetadata`:
  `device_model`, `lens`, `exposure_duration_seconds`, `iso`, `focus_lens_position`,
  `white_balance_gains`, `image_width`, `image_height`, `app_version`, `timestamp`).
- Generated Swift names: operation IDs lower camel case (`getTestSheetManifest`), type
  namespaces upper camel case (`Operations.GetTestSheetManifest`), properties lower camel
  case (`sheet_id` → `sheetId`, `safe_inset_mm` → `safeInsetMm`); JSON wire keys stay
  snake_case via CodingKeys.

### Operation IDs

OpenApiSpex synthesizes `ColorMatchingWeb.<Controller>.<action>` operation IDs. They are
valid but unwieldy in Swift (the generator mangles `.` to `_`), so the vendored document
assigns explicit operation IDs. These names are pinned by
`OpenAPISpecCoverageTests` and must not change without updating the tests:

| Path | Method | Pinned operationId | Generated method |
| --- | --- | --- | --- |
| `/api/v1/test_sheets/recent` | GET | `listRecentTestSheets` | `client.listRecentTestSheets` |
| `/api/v1/test_sheets/{sheet_id}/manifest` | GET | `getTestSheetManifest` | `client.getTestSheetManifest` |
| `/api/v1/test_sheets/{sheet_id}/ranked_results` | GET | `getRankedResults` | `client.getRankedResults` |
| `/api/v1/test_sheets/{sheet_id}/captures` | POST | `createCapture` | `client.createCapture` |
| `/api/v1/captures/{capture_id}/measurements` | POST | `uploadMeasurements` | `client.uploadMeasurements` |
| `/api/v1/captures/{capture_id}/judgments` | POST | `uploadJudgments` | `client.uploadJudgments` |

The other served routes (`printer_profiles`, `palettes`, `colors`, `metamer_pairs`,
`illuminant_measurements`, `multi_image_mapping`) stay in the vendored document as served;
the app does not call them (non-goal: new endpoints).

### Schema normalizations

1. **`CaptureRequest`** — the served schema mixes sibling `properties` with `anyOf`
   (flat legacy form OR nested `metadata` form). OpenAPIKit — used by
   swift-openapi-generator — drops sibling `properties` when `anyOf` is present, so the
   served shape generates an unusable wrapper with empty `value1`/`value2` objects. The
   vendored document keeps `type: object` with `properties.metadata` (`CaptureMetadata`)
   and `properties.quality` (`CaptureQuality`) and drops the `anyOf` (plus the flat
   legacy fields the iOS app never sends).
2. **`PairScoreRequest` → `PairScoreUpload`** — same sibling-`anyOf` problem. Vendored as
   a plain object: `pair_id` and `algorithm_version` required; `score`, `similarity`,
   `distance` optional numbers (the server resolves/clamps whichever is present).
3. **`TestSheetManifest` extension** — the served schema only guarantees `schema_version`,
   `sheet_id`, and `capture_profile.scoring_algorithm_version`. The server actually emits
   the full manifest (`sheet_version`, `manifest_url`, `created_at`, `page`,
   `registration_markers`, `printer_profile`, `capture_profile`, `patches`, `pairs`; see
   `ColorMatchingWeb.TestSheetJSON` upstream). The vendored document documents those
   fields with named components so the generated client covers what the app consumes.
   Named components added by vendoring: `SheetPage`, `SheetRect`, `RegistrationMarker`,
   `ManifestPatch`, `PairManifest`, `CaptureProfile`, `PrinterProfileManifest`.
4. **`RecentSheet`** — promoted from an inline array item to a named component.
5. **`MeasurementUploadItem` / `JudgmentUploadItem` / `PairScoreUpload`** — promoted from
   inline array items to named components.
6. **`MeasurementUploadItem.stats`** (`MeasurementStats` with `RgbTriple` channels) —
   vendored extension: the prose contract and the app send `stats`, the served spec does
   not document it. Documenting it preserves today's wire behavior with generated types.
7. **`MeasurementUploadRequest.scoring_algorithm_version`** — kept as an optional string
   (the app sends it; the server ignores it in favor of per-pair `algorithm_version`).
8. **`WhiteBalanceGains`** — promoted from a bare `{type: object}` to
   `{red, green, blue}` numbers required (the only shape the app sends).
9. **`RgbPayload` kept verbatim** (`anyOf` array | object | string) so the generated
   client exercises the served flexibility; the app uses the object variant
   (`.value2`).
10. **`RankedResults` kept verbatim** (only `schema_version` enum + `sheet_id`
    guaranteed), matching the served contract. The app does not consume the result rows
    yet; when it does, the schema must be extended upstream first.

`MeasurementUploadResponse` and `JudgmentUploadResponse` are kept verbatim: both uploads
respond `200` with a JSON body (`capture_id` + counts), not `204` as the prose contract
implied — see the deltas doc.

## App integration shape (for the implementation run)

- `ColorMatchingLPSAppCore.APIClient` becomes a thin adapter over the generated
  `Client` (`ColorMatchingOpenAPI.Client` + `URLSessionTransport`), keeping the public
  surface `ContentView` uses today: `fetchManifest(from:)`,
  `fetchManifest(baseURL:sheetCode:)`, `fetchRecentSheets`, `createCapture`,
  `uploadMeasurements`, `uploadJudgments`.
- Bearer auth: pass a `ClientMiddleware` to the generated client's
  `init(serverURL:configuration:transport:middlewares:)`; it adds
  `Authorization: Bearer <token>`. `GeneratedClientStubbedServerTests`
  demonstrates the middleware pattern.
- Hand-written API models (`CaptureMetadata`, `WhiteBalanceGains`,
  `CaptureSessionResponse`, `RecentSheet`, `PairJudgment`, upload request envelopes in
  `APIClient.swift`) are deleted; generated `Components.Schemas.*` types replace them.
- Purely client-side / domain models in `MeasurementCore` (`RGB`, `Rect`, `Point`,
  `Patch`, `PairManifest`, `SheetManifest`, `ChannelStats`, `PatchMeasurement`,
  `PairScore`, `CaptureQuality`) stay as-is; the adapter maps generated types onto them
  so `MeasurementCore` and the UI keep working unchanged.
- Regeneration is automatic on build via the build-tool plugin; no committed generated
  sources. Regenerate deliberately by bumping/re-snapshotting the vendored document and
  reviewing the build diff.
- CI note: plugin execution requires SwiftPM's sandbox to be disabled on Linux
  (`swift test --disable-sandbox` — verified). macOS runners run plain `swift test`.
- Red-phase validation notes (2026-11-02): the two new test files were compiled and run
  against a scratch package containing exactly the generated target described above:
  all 10 `GeneratedClientStubbedServerTests` tests passed, and all 13
  `OpenAPISpecCoverageTests` tests passed against a conforming vendored document.
  Two portability details surfaced and are already handled in the tests: required schema
  properties generate non-optional Swift properties, and URLSession may report
  `Content-Type: application/json; charset=utf-8`.

## Acceptance criteria → verification map

| Criterion | Verification | Where |
| --- | --- | --- |
| Vendored OpenAPI document covering the app's surfaces | Permanent unit test reading `iOS/OpenAPI/color-matching-v1.json` and asserting paths, pinned operation IDs, security scheme, and required response/request schemas | `iOS/Tests/ColorMatchingLPSAppTests/OpenAPISpecCoverageTests.swift` |
| Generated client exists and is wired into the package | `#if canImport(ColorMatchingOpenAPI)` red marker test fails until the module exists | `iOS/Tests/ColorMatchingLPSAppTests/GeneratedClientStubbedServerTests.swift` |
| Generated client exercised against stubbed responses (no live server): manifest, recent sheets, capture creation, measurement upload, judgment upload, ranked results | Six stubbed-transport tests asserting request line/headers/body JSON and decoded generated payloads | `iOS/Tests/ColorMatchingLPSAppTests/GeneratedClientStubbedServerTests.swift` |
| Hand-written API models replaced without changing wire behavior | Existing app-level client tests keep passing (measurement/judgment stubs updated from `204` to the published `200` + JSON body) | `iOS/Tests/ColorMatchingLPSAppTests/APIClientTests.swift` |
| Contract deltas recorded | Delta doc derived from the served spec, controllers, and JSON views | `docs/color-matching-api-contract-deltas.md` |
| `swift test --disable-sandbox` green with generated types | CI on macOS; no live server needed (all responses stubbed via `URLProtocol`) | `.github/workflows/ci.yml` |

Test placement rationale: the generated client is a permanent, regression-prone surface,
so its tests are permanent unit tests in the existing `ColorMatchingLPSAppTests` target
(no `.ephemeral-tests/` entry is needed for this issue).
