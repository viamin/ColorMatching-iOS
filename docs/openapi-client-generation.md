# Generated OpenAPI client for the iOS companion (issue #5)

This document is the tests-first plan for replacing the hand-written API layer
with a client generated by [swift-openapi-generator](https://github.com/apple/swift-openapi-generator)
from the OpenAPI document published by `viamin/color_matching` (upstream issue
#110, landed as upstream PR #113; the spec is served at
`GET /api/v1/openapi.json`).

The tests for this work were committed **before** the implementation (red
phase). This file records:

1. The acceptance-criterion → verification map.
2. The canonical layout/naming decisions the tests assume.
3. The contract deltas found between `docs/color-matching-api-contract.md`
   (prose) and the published spec — lift this table into the PR description.
4. The re-vendor workflow.

## Acceptance-criterion → verification map

| AC | Deliverable | Smallest credible verification | Where |
|----|-------------|--------------------------------|-------|
| AC-1 | Generator + runtime deps; spec fetched/vendored | Permanent unit test asserting the vendored document exists, parses, declares OpenAPI 3, bearer auth, and the six app surfaces with upstream operationIds | `iOS/Tests/ColorMatchingLPSAppTests/OpenAPISpecContractTests.swift` |
| AC-2 | Client generated for the six surfaces | Permanent unit tests exercising every generated operation against a stubbed `ClientTransport` (path, method, body, decoded response) | `iOS/Tests/ColorMatchingLPSAppTests/GeneratedClientStubbedResponseTests.swift` |
| AC-3 | Hand-written API models replaced; client-only models kept | `swift test --disable-sandbox` green after wiring (existing `APIClientTests` are updated/retired in the implementation run); review confirms `MeasurementCore` client-side models untouched | Implementation run |
| AC-4 | Swift tests against local stubbed responses, no live server | The stubbed-transport tests above use `StubTransport`; no network in CI | `GeneratedClientStubbedResponseTests.swift` |
| AC-5 | PR description records contract deltas + endpoint gaps | Delta table below (inspectable artifact); PR description at implementation time | This file + PR body |

## Canonical layout the tests assume

The tests are coupled to the following decisions. If the implementation
deviates, update the tests mechanically — the coupling is intentional so the
PR diff shows exactly what the generated client replaced.

- Vendored spec (verbatim, JSON, upstream operationIds preserved):
  `iOS/Sources/OpenAPIGeneratedClient/openapi.json`
- Generated client target: `OpenAPIGeneratedClient`
  (plugin `OpenAPIGenerator` from `apple/swift-openapi-generator`,
  runtime dependency `OpenAPIRuntime` from `apple/swift-openapi-runtime`).
- `ColorMatchingLPSAppCore` depends on `OpenAPIGeneratedClient` and keeps a
  thin facade (bearer-token `ClientMiddleware` + mapping to client-side
  models) that replaces the hand-rolled request/response encoding in
  `APIClient.swift`.
- Test target `ColorMatchingLPSAppTests` declares dependencies on
  `OpenAPIGeneratedClient` and `OpenAPIRuntime`. Until then the
  generated-client tests are compiled out by
  `#if canImport(OpenAPIGeneratedClient) && canImport(OpenAPIRuntime)`
  and an `XCTFail` availability test marks the missing deliverable (red
  phase).
- `swift test` picks the new test files up automatically (SPM target
  directory membership). The `ColorMatchingLPS.xcodeproj` project lists test
  files explicitly, so the implementation run must also add
  `OpenAPISpecContractTests.swift` and
  `GeneratedClientStubbedResponseTests.swift` to the Xcode test target for
  the `xcodebuild` CI leg to compile them.

### Generated symbol naming (why the method names look odd)

Upstream `open_api_spex` derives operationIds as `Module.action` (dots), and
the spec is vendored verbatim so drift shows up as a regeneration diff.
swift-openapi-generator's `SafeNameGenerator` maps `.` → `_` without
capitalizing the next word, `-`/`/`/`_` to word separators (next word
capitalized), and snake_case properties to camelCase:

| operationId (spec) | generated method | Input/Output suffix types |
|---|---|---|
| `ColorMatchingWeb.TestSheetController.manifest` | `colorMatchingWeb_TestSheetController_manifest` | `ColorMatchingWeb_TestSheetController_manifestInput/Output` |
| `ColorMatchingWeb.TestSheetController.recent` | `colorMatchingWeb_TestSheetController_recent` | `…recentInput/Output` |
| `ColorMatchingWeb.TestSheetController.ranked_results` | `colorMatchingWeb_TestSheetController_ranked_results` | `…ranked_resultsInput/Output` |
| `ColorMatchingWeb.CaptureController.create` | `colorMatchingWeb_CaptureController_create` | `…createInput/Output` |
| `ColorMatchingWeb.CaptureController.upload_measurements` | `colorMatchingWeb_CaptureController_upload_measurements` | `…upload_measurementsInput/Output` |
| `ColorMatchingWeb.CaptureController.upload_judgments` | `colorMatchingWeb_CaptureController_upload_judgments` | `…upload_judgmentsInput/Output` |

Response cases come from the generator's status-code table: `200 → .ok`,
`201 → .created`, `401 → .unauthorized`, `404 → .notFound`,
`422 → .unprocessableContent`. String-enum cases: `lps-sheet-manifest/v1 →
.lpsSheetManifestV1`, `lps-distance-v1 → .lpsDistanceV1`,
`lps-ranked-results/v1 → .lpsRankedResultsV1`. `RgbPayload`'s anyOf becomes
`case1` ([Double]), `case2` (r/g/b object), `case3` (String).

## Contract deltas: prose contract vs published spec

Comparison base: `docs/color-matching-api-contract.md` vs the schema modules
merged in upstream PR #113 (`lib/color_matching_web/api_schemas.ex`,
`test_sheet_controller.ex`, `capture_controller.ex`).

| # | Area | Prose contract | Published spec |
|---|------|----------------|----------------|
| 1 | Sheet manifest response | Documents `sheet_version`, `manifest_url`, `created_at`, `page`, `registration_markers`, `printer_profile`, `patches`, `pairs` | Only requires `schema_version` (enum `lps-sheet-manifest/v1`), `sheet_id`, `capture_profile.scoring_algorithm_version` (enum `lps-distance-v1`); the geometry the iOS analyzer consumes is **not schema-typed** (passes as undeclared additional properties, invisible to the generated client) |
| 2 | Capture request | Single nested shape: `metadata` + `quality` | `anyOf`: the nested shape **or** a flat payload. Flat renames: `exposure_duration` (not `exposure_duration_seconds`), `rejection_reasons` (not `rejections`). Nested `quality` matches prose keys but has **no required list** |
| 3 | Measurement upload request | Top-level `scoring_algorithm_version`; per-measurement `stats` (`sample_count`, `clipping_fraction`, `mean`, `standard_deviation`) | Neither is declared. `stats` fields the app computes today cannot be sent through the generated types (silently dropped). `normalized_linear_rgb_median` is **required** (iOS model had it optional) |
| 4 | RGB payloads | Fixed `{r,g,b}` object | `RgbPayload` anyOf: number array, `{r,g,b}` object, or string — generated type is an enum the client must handle |
| 5 | Measurement upload response | No body documented (any 2xx = success) | HTTP 200 with required `capture_id`, `measurement_count`, `pair_score_count` |
| 6 | Judgment upload response | No body documented | HTTP 200 with required `capture_id`, `judgment_count` |
| 7 | Ranked results | "source colors, scores, labels, capture provenance, printer profile, scoring algorithm version" | Only `schema_version` (enum `lps-ranked-results/v1`) + `sheet_id` required; the promised payload is **not typed** |
| 8 | Capture create status | No status documented | 201 + `capture_id`; 401/404/422 with `ErrorResponse` (`errors` object or array with `detail`/`source.pointer`) |
| 9 | Auth | "shared bearer token", optionally off in dev | `bearerAuth` (http/bearer) security scheme declared on every app operation; 401 responses documented |
| 10 | Pair score request | `pair_id`, `distance`, `similarity`, `algorithm_version` | Requires `pair_id` + `algorithm_version` plus anyOf `score`/`similarity`/`distance` (a superset — `score` is new) |

### Endpoint gaps discovered

- **None of the six app surfaces are missing** from the spec — all six paths
  exist with the expected methods and operationIds.
- The spec documents **7 additional endpoint groups** the prose contract never
  mentioned: `printer_profiles` (+`/colors`, `/metamer_pairs`), `palettes`,
  `colors`, `illuminant_measurements` (+`/bulk`), `multi_image_mapping`, and
  `openapi.json` itself. They generate types too; the app just ignores them.
- Under-specified surfaces (manifest geometry, ranked-results payload,
  measurement `stats`) are gaps **on the server side** — the iOS tests can only
  pin what the spec declares. Follow up upstream if drift bites there.

## Re-vendor workflow

```bash
# From a running color_matching instance (dev allows unauthenticated spec reads):
curl -fsS "$BASE_URL/api/v1/openapi.json" \
  -o iOS/Sources/OpenAPIGeneratedClient/openapi.json
```

Then rebuild; `swift test --disable-sandbox` (run from `iOS/`) re-runs
`OpenAPISpecContractTests` against the newly vendored document, so server-side
drift surfaces as a test failure or a regeneration diff.

## Test execution notes

- No live server is used anywhere: the generated client is exercised through a
  stubbed `ClientTransport`; the spec tests read the vendored JSON file
  located relative to `#filePath`.
- The container that authored these tests has no Swift toolchain; the red
  failures are expected to be observed in CI (`swift test` on macOS). The
  spec-coverage tests fail today because the vendored document does not exist
  yet, and the availability test fails because the generated module is not
  wired into the package yet — both are the red-phase evidence for issue #5.
