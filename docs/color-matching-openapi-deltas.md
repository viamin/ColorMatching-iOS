# Contract Deltas: Prose Contract vs Published OpenAPI Spec

Comparison of `docs/color-matching-api-contract.md` (the hand-written prose
contract) against the machine-readable OpenAPI 3 spec published by
viamin/color_matching at `GET /api/v1/openapi.json` (issue
viamin/color_matching#110, closed 2026-10-30). The published spec is
generated by OpenApiSpex from `ColorMatchingWeb.ApiSpec` and the
controller operation specs; it was reconstructed for this comparison from
the `main` branch on 2026-11-02.

The vendored copy used to generate the Swift client lives at
`docs/color-matching-openapi-v1.yaml` and is copied verbatim to
`iOS/Sources/ColorMatchingOpenAPI/openapi.yaml` by the implementation.

This document is the source for the "what changed between the prose
contract and the published spec" section of the PR description.

## How the deltas were established

Every delta below was checked against the actual server implementation,
not only the spec:

* `lib/color_matching_web/api_schemas.ex` — published component schemas.
* `lib/color_matching_web/controllers/test_sheet_controller.ex`,
  `capture_controller.ex`, `color_palette_controller.ex` — operation
  shapes (parameters, request bodies, status codes).
* `lib/color_matching_web/controllers/test_sheet_json.ex` — the JSON the
  server actually renders for manifest/recent/ranked results.

## 1. Behavior deltas the app must adopt (visible in the new tests)

| # | Surface | Prose contract | Published spec / server | Consequence |
|---|---------|----------------|-------------------------|-------------|
| D1 | `POST /captures/{id}/measurements` response | Unspecified; the app treated any 2xx as success and sent with no expectation of a body (`204` tolerated) | `200` with JSON body `MeasurementUploadResponse` `{capture_id, measurement_count, pair_score_count}` | App can now verify the server accepted every measurement and score (`measurement_count`/`pair_score_count`) |
| D2 | `POST /captures/{id}/judgments` response | Unspecified; app expected no body | `200` with JSON body `JudgmentUploadResponse` `{capture_id, judgment_count}` | App can confirm the judgment count |
| D3 | Measurement upload payload | Per-measurement `stats` block (`sample_count`, `clipping_fraction`, `mean`, `standard_deviation`) and top-level `scoring_algorithm_version` | Neither exists in the published `MeasurementUploadRequest` schema; the server persists only `patch_id`, `linear_rgb_median`, `normalized_linear_rgb_median`; algorithm version lives per pair score (`PairScoreRequest.algorithm_version`) | Spec-conformant uploads drop `stats` and the top-level algorithm version. The server silently ignored these fields — exactly the runtime-drift class of bug this issue exists to remove |
| D4 | Measurement item requirements | `normalized_linear_rgb_median` optional, `stats` required | `normalized_linear_rgb_median` **required** (server rejects a measurement without it), `stats` absent | App must always upload normalized medians (it already computes them) |
| D5 | Capture creation | Nested `metadata` + `quality` only | Schema also accepts a **legacy flat form** (`device_model`, `lens`, `exposure_duration` [sic — no `_seconds`], `iso`, `focus_lens_position`, `white_balance_gains`, `image_width`, `image_height`, `app_version`, `timestamp`, `detected_marker_count`, `blur_score`, `rejection_reasons` [sic — not `rejections`]) via `anyOf` | App keeps the nested form (both accepted); the flat form is documented but unused |
| D6 | Capture response status | Unspecified | `201` (not `200`) with `{capture_id}` | The server renders `capture_id` as `Integer.to_string(capture.id)` — a stringified numeric DB id (e.g. `"9"`), not the opaque `capture_123` style of the prose example. Generated client types it as a string; the app treats it as an opaque token |
| D7 | `iso` metadata field | Number (example `100`, no type constraint) | `integer` (minimum 0, exclusive) | App must send integral ISO values (camera code currently produces `Float`; rounded at the facade boundary) |
| D8 | `POST /test_sheets/{id}/captures` validation failure | Unspecified | `422` with `ApiErrorResponse` (`errors` as object or array of `{detail, source}`) plus `401`/`404` | Facade maps these to typed errors instead of the previous blanket `badStatus` |

## 2. Endpoint / schema gaps (spec is thinner than the prose contract)

These fields are rendered by the server (verified in
`test_sheet_json.ex`) and required by the app, but the published spec does
not validate them. The vendored copy gap-fills them; each is marked
`[vendored gap-fill]` inline so a future upstream regeneration shows a
clean diff.

* **G1 — Manifest geometry**: published `TestSheetManifest` requires only
  `schema_version`, `sheet_id`, `capture_profile`. The page geometry
  (`page`, `registration_markers`, `patches`, `pairs`, `sheet_version`,
  `manifest_url`, `created_at`, `printer_profile`) that the app needs to
  drive `SheetAnalyzer` is rendered but unvalidated. Vendored copy
  validates all of it.
* **G2 — Ranked results payload**: published `RankedResults` requires only
  `schema_version`, `sheet_id`. The prose contract demands source colors,
  scores, labels, capture provenance, printer profile, and scoring
  algorithm version — all of which the server renders (`results[]` with
  `rank`, `pair_id`, `scoring_algorithm_version`, `row`, `col`,
  `source_colors{color_a_hex,color_b_hex}`, aggregate `score`, judgments,
  observation counts). Vendored copy adds the full shape. This is the
  biggest upstream gap; ideally fixed in viamin/color_matching by
  formalizing `RankedResults`.
* **G3 — `white_balance_gains`**: freeform object in the spec; the app
  always emits `{red, green, blue}` channel gains. Vendored copy pins that
  shape.
* **G4 — `GET /api/v1/openapi.json`** is excluded from the published spec
  itself (`operation :show, false`), as are the `match(:*, ...)` 405
  routes — the vendored copy mirrors both exclusions.

## 3. Real-vs-prose field-name deltas (server render code)

Found while reconstructing the actual manifest payload; the prose contract
is wrong or imprecise here:

* **N1** — Patch IDs are `"{pair_id}#{side}"` (e.g. `pair_1#first`), not
  `patch_1` as in the prose example. The app treats patch IDs as opaque.
* **N2** — Manifest `printer_profile` uses
  `{printer_make_model, paper_type, ink_type, icc_profile, print_settings,
  driver_name, driver_version, calibration_date, calibration_version,
  notes}`; the prose example claimed `{id, name, paper, ink, settings}`.
* **N3** — `recent` sheets always render `title: null` today; the schema
  keeps `title` required-but-nullable so the app must keep handling both.
* **N4** — Ranked results use a nested `score` aggregate
  (`{average, latest, minimum, maximum, capture_count, sample_count,
  algorithm_versions}`), not a single `distance`/`similarity` pair.

## 4. Vendoring normalizations (documented deviations)

Applied only where swift-openapi-generator cannot express the published
construct or where the published construct admits wire shapes the app
never emits. Every one is also marked inline in the vendored YAML.

* **V1** — `CaptureRequest.anyOf` (required-only branches expressing
  "nested or flat") dropped; `metadata` made required instead. Same
  validation intent, representable in Swift types.
* **V2** — `RgbPayload.anyOf` (array | `{r,g,b}` | string) pinned to the
  `{r,g,b}` object form the app emits.
* **V3** — `PairScoreRequest.anyOf` (score | similarity | distance)
  replaced by optional `similarity`/`distance` properties (the app sends
  both plus required `algorithm_version`).
* **V4** — Inline object schemas promoted to named components:
  `RecentSheet`, `PairJudgment`, `MeasurementUploadItem`,
  `CaptureQualityPayload` (upstream defines them inline; promotion keeps
  generated type names stable and reviewable).

## 5. Upstream follow-ups suggested by this audit

1. Formalize manifest geometry and ranked-results payloads in
   viamin/color_matching's `ApiSchemas` (removes gap-fills G1/G2).
2. Tighten `RgbPayload` and `PairScoreRequest` to the shapes clients
   actually send (V2/V3), or keep permissive but document.
3. Consider committing the generated `openapi.json` or exposing a build
   artifact so the iOS repo can vendor it byte-for-byte instead of
   reconstructing from source.
