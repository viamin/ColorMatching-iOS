# Contract deltas: prose contract vs published OpenAPI spec

Status: **analysis for the OpenAPI client migration (issue #5)**. This document is the
source material for the PR description required by issue #5 ("what changed between the
prose contract and the published spec, and any endpoint gaps discovered").

- Prose contract (this repo): `docs/color-matching-api-contract.md`
- Published spec (upstream): served by `viamin/color_matching` at `GET /api/v1/openapi.json`,
  published in viamin/color_matching#110 (closed by viamin/color_matching#113), generated by
  `open_api_spex` from `lib/color_matching_web/api_spec.ex`, `lib/color_matching_web/api_schemas.ex`,
  and the controller `operation` declarations.
- Upstream revision reviewed: `viamin/color_matching@47057afd58f7d46b4d4b740ca7d2d08947774471` (main)

## Endpoint-by-endpoint deltas

### GET /api/v1/test_sheets/:sheet_id/manifest

Prose and spec agree on: `schema_version` (`lps-sheet-manifest/v1`, now a spec enum),
`sheet_id`, `sheet_version`, `manifest_url`, `created_at`, `page`, `registration_markers`,
`capture_profile` (with `scoring_algorithm_version` pinned to `lps-distance-v1` as a spec enum),
`patches`, `pairs`.

Deltas:

1. **`printer_profile` is completely reshaped.** The prose contract documents
   `{id, name, paper, ink, settings}`. The published API renders
   `{id, printer_make_model, paper_type, ink_type, icc_profile, print_settings, driver_name,
   driver_version, calibration_date, calibration_version, notes}` (see
   `ColorMatchingWeb.TestSheetJSON.render_printer_profile/1`). The iOS `SheetManifest`
   model never decoded `printer_profile`, so no app behavior changes; generated types will
   now carry the real shape.
2. **Patch IDs are structured strings.** The real renderer emits
   `"{pair_id}#first"` / `"{pair_id}#second"` (e.g. `pair_1#first`), and
   `pairs[].first_patch_id`/`second_patch_id` use the same convention. The prose example
   (`patch_1`, with `first_patch_id: patch_1`) implied opaque IDs. The app already treats
   IDs as opaque, but tests and fixtures must use the real format.

### GET /api/v1/test_sheets/recent

Shape unchanged (`{sheets: [{sheet_id, manifest_url, title}]}`). `title` is nullable and
the current server always renders it as `null`; the prose contract's "may be null" holds.

### POST /api/v1/test_sheets/:sheet_id/captures

1. The spec accepts the capture attributes either **flat or nested** under `metadata`
   (`anyOf` in `CaptureRequest`); the app sends the nested `{metadata, quality}` form,
   which remains valid.
2. **Response is `201` with `{"capture_id": "..."}`** where the real ID is a stringified
   integer (`"42"`), not the prose example's `capture_123` prefix form. No code depends on
   the prefix.

### POST /api/v1/captures/:capture_id/measurements

1. **The published spec omits two fields the prose contract documented:**
   - top-level `scoring_algorithm_version`
   - the per-measurement `stats` block (`sample_count`, `clipping_fraction`, `mean`,
     `standard_deviation`)

   The server's CastAndValidate tolerates extra properties, so the old app payload was
   accepted, but those fields were never part of the published contract. The generated
   client therefore sends only spec-declared fields: `measurements[]` with
   `{patch_id, linear_rgb_median, normalized_linear_rgb_median}` and `pair_scores[]` with
   `{pair_id, algorithm_version, score | similarity | distance}`.
   `algorithm_version` moves to each pair score (the app already sends it there).
2. **`normalized_linear_rgb_median` is required** by the spec schema (anyOf r/g/b object,
   array, or encoded string). The app uploads `analysis.normalizedMeasurements`, which
   always carries normalized medians, so this is satisfied on the normal path.
3. **Response body added:** `200` with
   `{capture_id, measurement_count, pair_score_count}` (all required). The prose contract
   documented no response; the app treated the call as fire-and-forget. The new client
   surfaces the receipt.

### POST /api/v1/captures/:capture_id/judgments

Shape of the request matches the prose contract. **Response body added:** `200` with
`{capture_id, judgment_count}` (both required). Again previously fire-and-forget.

### GET /api/v1/test_sheets/:sheet_id/ranked_results

The prose contract described this endpoint in one sentence with **no schema**. The
published API pins `lps-ranked-results/v1`:

```
{
  "schema_version": "lps-ranked-results/v1",
  "sheet_id": "...",
  "printer_profile": { ...same shape as manifest... },
  "capture_count": N,
  "latest_capture_at": "...", "earliest_capture_at": "...",
  "scoring_algorithm_versions": ["lps-distance-v1"],
  "results": [{
    "rank": 1, "pair_id": "pair_1", "scoring_algorithm_version": "lps-distance-v1",
    "row": 0, "col": 1,
    "source_colors": {"color_a_hex": "#FF0000", "color_b_hex": "#00FF00"},
    "score": {"average", "latest", "minimum", "maximum", "capture_count", "sample_count", "algorithm_versions"},
    "current_judgment": "near_match" | null,
    "current_judgment_observed_at": "..." | null,
    "observation_count": N,
    "latest_observation": {"judgment", "observed_at"} | null,
    "capture_count": N, "latest_capture_at": "...", "earliest_capture_at": "..."
  }]
}
```

This endpoint had **no client method at all** in the iOS app; the migration adds
`fetchRankedResults(sheetID:baseURL:)` mapping the fields the app displays
(rank, pair_id, row/col, source colors, average/latest score, current judgment).

## Endpoint gaps discovered

Endpoints present in the published spec but absent from the prose contract (none used by
the iOS app today; recorded so the regeneration diff is understandable):

- `GET /api/v1/openapi.json` (the spec itself)
- `GET /api/v1/printer_profiles`
- `GET /api/v1/printer_profiles/:printer_profile_id/colors`
- `GET /api/v1/printer_profiles/:printer_profile_id/metamer_pairs`
- `GET /api/v1/palettes`
- `GET /api/v1/colors`
- `POST /api/illuminant_measurements`, `POST /api/illuminant_measurements/bulk`
- `POST /api/multi_image_mapping`

Authentication: every app surface declares the `bearerAuth` security scheme in the spec
(`http`/`bearer`), matching the prose contract's shared bearer token.

## Migration decisions pinned by the new tests

- The OpenAPI document is vendored at `iOS/OpenAPI/color-matching.json` (fetched from
  `GET /api/v1/openapi.json`), validated by `OpenAPISpecCoverageTests`.
- The upload payload is pinned to the spec-declared key sets (no undeclared
  `scoring_algorithm_version`/`stats` extras).
- Upload responses are decoded into typed receipts
  (`MeasurementUploadResponse`, `JudgmentUploadResponse`).
- New ranked-results surface: `RankedResults` / `RankedPairResult` mapped from the
  generated types.
