# OpenAPI contract deltas: prose contract vs. published spec

Status: recorded as part of issue #5 ("Replace hand-written API layer with a
generated OpenAPI Swift client"). This document is the source material for the
PR description deliverable ("what changed between the prose contract and the
published spec, and any endpoint gaps discovered") and the implementation plan
the follow-up run executes.

Sources compared:

- Prose contract: `docs/color-matching-api-contract.md` (hand-written, in this repo)
- Published spec: `color_matching` serves `GET /api/v1/openapi.json` (OpenAPI 3.0,
  generated by `open_api_spex` from the router + controller specs; published by
  viamin/color_matching#110, merged as viamin/color_matching#113)

Upstream source files consulted: `lib/color_matching_web/api_spec.ex`,
`lib/color_matching_web/api_schemas.ex`, `lib/color_matching_web/router.ex`,
`lib/color_matching_web/controllers/test_sheet_controller.ex`,
`lib/color_matching_web/controllers/capture_controller.ex`,
`lib/color_matching_web/controllers/test_sheet_json.ex`.

## Verdict

The six surfaces the app uses exist in the published spec with matching paths
and HTTP methods, bearer auth, and versioned schema strings. Four surfaces are
directly consumable by swift-openapi-generator. Two request payloads
(`CaptureRequest`, `PairScoreRequest`) use a `properties` + `anyOf` composition
that OpenAPIKit-based tooling silently drops, so the generated Swift types for
those payloads are empty — capture creation and pair-score upload cannot ride
the generated client until upstream fixes the composition. Several response
schemas under-document what the server actually renders.

## Per-surface deltas

### `GET /api/v1/test_sheets/{sheet_id}/manifest`

| Aspect | Prose contract | Published spec | Delta |
| --- | --- | --- | --- |
| Declared fields | Full manifest (schema_version, sheet_version, sheet_id, manifest_url, created_at, page, registration_markers, printer_profile, capture_profile, patches, pairs) | Only `schema_version`, `sheet_id`, `capture_profile.scoring_algorithm_version` are declared | **Gap**: generated types surface 3 fields only; the rest are undocumented (allowed but dropped) |
| Patch IDs | `patch_1` style | Rendered as `"pair_1#first"` / `"pair_1#second"` (composite) | Naming delta |
| Printer profile | `{id, name, paper, ink, settings}` | Rendered as `{printer_make_model, paper_type, ink_type, icc_profile, print_settings, driver_name, driver_version, calibration_date, calibration_version, notes}` (undocumented) | Shape delta (undocumented) |
| Errors | Undocumented | 401 + 404 documented as `ApiErrorResponse` | Spec is richer |

The server-rendered manifest (see `ColorMatchingWeb.TestSheetJSON.manifest/1`)
matches the prose contract shape for `page`, `registration_markers`,
`capture_profile`, `patches`, `pairs` — but none of that is declared in the
schema, so the generated client types cannot see it. Until upstream documents
these fields, the app keeps its client-side manifest decoding (patches/pairs
drive `SheetAnalyzer`); only the three declared fields come from generated
types. **Follow-up needed upstream.**

### `GET /api/v1/test_sheets/recent`

Matches the prose contract: `sheets[]` with `sheet_id`, `manifest_url`,
`title` (nullable, and required-but-nullable in the spec). No delta.

### `POST /api/v1/test_sheets/{sheet_id}/captures`

| Aspect | Prose contract | Published spec | Delta |
| --- | --- | --- | --- |
| Request body | `{metadata: {...}, quality: {...}}` (nested only) | `anyOf`: flat top-level body **or** `{metadata}`; `quality` is a sibling property required by neither branch | Spec adds a flat variant; `quality` effectively optional |
| Flat-variant field names | `exposure_duration_seconds`, `rejections` | `exposure_duration`, `rejection_reasons` | Renamed in flat variant |
| `CaptureMetadata` required fields | None stated | `device_model, lens, image_width, image_height, app_version, timestamp` | Stricter |
| Response | 201 `{capture_id}` | Same | No delta |

**Blocking gap:** `CaptureRequest` declares sibling `properties` alongside
`anyOf`. OpenAPIKit (both the 3.0 and 3.1 decoders used by
swift-openapi-generator) returns early on `anyOf` and drops sibling
`properties`, and the `anyOf` branches themselves contain only `required`
lists (no `properties`), which the generator skips with warnings. The
generated `CaptureRequest` therefore encodes to `{}` and cannot carry
metadata/quality. Upstream fix options: put the fields inside the `anyOf`
branches, or model the nested/flat choice with `oneOf` + full property maps.
Until then, capture creation stays on the existing hand-written encoding.

### `POST /api/v1/captures/{capture_id}/measurements`

| Aspect | Prose contract | Published spec | Delta |
| --- | --- | --- | --- |
| Top-level `scoring_algorithm_version` | Present | Absent from schema | Dropped (server tolerates unknown keys, but generated types cannot send it) |
| Measurement `stats` block (`sample_count`, `clipping_fraction`, `mean`, `standard_deviation`) | Present | Absent from schema | **Gap**: generated types cannot send stats |
| `normalized_linear_rgb_median` | Optional | Required on every row | Stricter |
| RGB encoding | Object `{r,g,b}` only | `RgbPayload` anyOf: number array / `{r,g,b}` object / string | Richer |
| `pair_scores[].*` | `{pair_id, distance, similarity, algorithm_version}` | `PairScoreRequest`: `pair_id`+`algorithm_version` required, `score`/`similarity`/`distance` anyOf | Restructured |
| Top-level `required` | n/a | Neither `measurements` nor `pair_scores` required | Looser |
| Response | Undocumented (app sends and treats 2xx/204 as success) | 200 `{capture_id, measurement_count, pair_score_count}` | Spec documents a JSON body the app should read |

**Blocking gap:** `PairScoreRequest` has the same sibling-`properties` +
`anyOf` composition problem as `CaptureRequest`; its generated type cannot
carry `pair_id`/`algorithm_version`/score fields. Measurement rows themselves
(patch_id + RGB medians) generate fine. Until upstream fixes the composition,
pair-score upload stays on the existing hand-written encoding.

### `POST /api/v1/captures/{capture_id}/judgments`

Request matches the prose contract (`judgments[]` with `pair_id`, `judgment`;
judgment values are free-form strings — the prose enum `match`/`near_match`/
`no_match` is not enforced in the schema). Response delta: spec documents 200
`{capture_id, judgment_count}` where the prose contract documented none and
the app treated 204 as success. Fully usable from generated types.

### `GET /api/v1/test_sheets/{sheet_id}/ranked_results`

Prose contract is deliberately vague ("source colors, scores, labels, capture
provenance, printer profile, and scoring algorithm version"). The published
schema declares only `schema_version` (`lps-ranked-results/v1`) + `sheet_id`,
while the rendered payload (`ColorMatchingWeb.TestSheetJSON.ranked_results/1`)
is rich: per-pair `rank`, `score` stats (average/latest/min/max/counts),
`current_judgment`, observation provenance, capture counts, algorithm
versions. **Gap:** generated types surface 2 fields only; upstream needs to
document the result rows before the app can consume ranked results through
generated types.

## Cross-cutting deltas

- **operationIds**: open_api_spex derives module-qualified ids
  (`ColorMatchingWeb.TestSheetController.manifest`,
  `ColorMatchingWeb.TestSheetController.recent`,
  `ColorMatchingWeb.TestSheetController.ranked_results`,
  `ColorMatchingWeb.CaptureController.create`,
  `ColorMatchingWeb.CaptureController.upload_measurements`,
  `ColorMatchingWeb.CaptureController.upload_judgments`). The vendored document
  must not be rewritten; the generator's `nameOverrides` maps them to Swift
  method names (see plan below).
- **Extra endpoints** in the published spec that the app does not use:
  `printer_profiles` (+ colors, metamer_pairs), `palettes`, `colors`,
  `illuminant_measurements` (+ `/bulk`), `multi_image_mapping`. The generator
  config filters to the six app operations.
- **Auth**: `bearerAuth` (http/bearer) security scheme matches the prose
  contract. The generated client gets it via a `ClientMiddleware` that injects
  the `Authorization` header (there is no per-operation credential in the
  spec).
- **Error shape**: `ApiErrorResponse.errors` is itself an `anyOf` (object /
  array of `{detail, source}`) — fine for decoding non-2xx cases, but
  consumers should treat it loosely.

## Implementation plan (follow-up run)

Target layout (all inside the existing SwiftPM package; no new targets):

```
iOS/
├── Package.swift                  # add deps + plugin (see below)
└── Sources/ColorMatchingLPSAppCore/
    ├── openapi.json               # vendored verbatim from GET /api/v1/openapi.json
    └── openapi-generator-config.yaml
```

`Package.swift` additions:

- `.package(url: "https://github.com/apple/swift-openapi-generator", from: "1.8.0")`
- `.package(url: "https://github.com/apple/swift-openapi-runtime", from: "1.8.0")`
- `.package(url: "https://github.com/apple/swift-openapi-urlsession", from: "1.8.0")`
- `ColorMatchingLPSAppCore` target: dependencies
  `OpenAPIRuntime` (swift-openapi-runtime) and `OpenAPIURLSession`
  (swift-openapi-urlsession); plugin
  `.plugin(name: "OpenAPIGenerator", package: "swift-openapi-generator")`
- `ColorMatchingLPSAppTests` test target: additional dependency
  `OpenAPIRuntime` (activates the `#if canImport(OpenAPIRuntime)` tests).

Version floor 1.8.0: HTTPTypes-based `ClientTransport` (present since 1.5) and
`nameOverrides`/`filter` config support. 1.13.x is current.

`openapi-generator-config.yaml` (exact contents):

```yaml
generate:
  - types
  - client
accessModifier: public
filter:
  operations:
    - ColorMatchingWeb.TestSheetController.manifest
    - ColorMatchingWeb.TestSheetController.recent
    - ColorMatchingWeb.TestSheetController.ranked_results
    - ColorMatchingWeb.CaptureController.create
    - ColorMatchingWeb.CaptureController.upload_measurements
    - ColorMatchingWeb.CaptureController.upload_judgments
nameOverrides:
  ColorMatchingWeb.TestSheetController.manifest: getTestSheetManifest
  ColorMatchingWeb.TestSheetController.recent: listRecentTestSheets
  ColorMatchingWeb.TestSheetController.ranked_results: getRankedResults
  ColorMatchingWeb.CaptureController.create: createCapture
  ColorMatchingWeb.CaptureController.upload_measurements: uploadMeasurements
  ColorMatchingWeb.CaptureController.upload_judgments: uploadJudgments
```

If the pinned generator version does not apply `nameOverrides` to operation
method names, fall back to normalizing the operationIds when vendoring (record
which mechanism was used); the tests target the resulting Swift method names
either way.

Vendoring: fetch verbatim from a running `color_matching`:

```bash
curl -fsS "$SERVER/api/v1/openapi.json" \
  -o iOS/Sources/ColorMatchingLPSAppCore/openapi.json
```

App integration (bounded by the issue's non-goals — no capture/scoring
behavior changes):

- `APIClient` routes manifest/recent/ranked/judgments (and measurement rows)
  through the generated `Client` + `URLSessionTransport` + bearer
  `ClientMiddleware`; response decoding uses generated types.
- Purely client-side models stay as-is: `RGB`, `Rect`, `Point`, `Page`,
  `ChannelStats`, `PatchMeasurement`, `PairScore`, `SampleOverlayRegion`,
  `SheetAnalysis`, `DetectedMarker` (analysis domain, not API contract).
- Hand-written API Codable models that duplicate generated types are deleted
  (`RecentSheet`, `CaptureSessionResponse` wire structs); manifest
  patch/pair/page decoding stays client-side until upstream documents those
  fields (gap above).
- Capture creation and pair-score upload keep the existing hand-written
  request encoding until upstream fixes the `anyOf` composition (gaps above);
  add upstream follow-up issues and link them in the PR description.
